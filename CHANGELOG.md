# Changelog

All notable changes to this project are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0, minor versions may make breaking changes to the `v1alpha1` API; they are listed under "Changed".

## [Unreleased]

### Upgrade notes

- Plain `evalsi doctor` now checks only SDK scoring and does not inspect or
  launch optional execution tools. Use `doctor --all` for the previous optional
  diagnostic inventory; `--require server` and `--require agent` retain explicit
  required-capability checks.

- **The webhook destination guard is on by default.** A webhook URL must be HTTPS to a public address unless its host is listed under `webhooks.allow_hosts` (exact or `*.domain`; Helm `webhooks.allowHosts`; hosts of `bootstrap.webhooks` are allowed automatically). Webhooks saved earlier whose URL is plain HTTP or an internal address (in-cluster service names, private IPs) now fail each delivery at once with an error naming the setting, and the server logs `webhook destination refused` at start. List their hosts and restart, or set `webhooks.ssrf_guard: false` for the old behaviour. Deliveries that failed meanwhile are not resent.

- **Rate limits** shared across replicas (`rate_limits.shared`, decision 0036) with a per-replica fallback and metrics, and live reload of rates, principals and `disabled`.
- **`evalsi.log()` retries** failed batches with backoff, `Retry-After` and a stable `Idempotency-Key`.
- **Keyless image signatures:** `sandbox.image_signatures.keyless` and `trusted_root` verify Fulcio and Rekor signatures (`.sig` tag and sigstore referrer bundles). Tested against a stand-in CA only.
- **Online sandbox-time quota:** online policies, guardrails, Wasm evaluators and reward rollouts count toward `sandbox_seconds_per_day` (decision 0037).
- **Quality scores for routing:** `GET /v1alpha1/quality` and `quality_exports` publish per-group quality, with an agentgateway recipe (decision 0038).
- **Adapters:** BFCL `web_search_*` and `memory_*` categories; τ-bench `user=tau2` uses tau2's own LiteLLM user simulator.
- **Tutorials** (`docs/tutorials/`): ten walkthroughs from a first install to a CI gate, driving the built-in harness with TinyLM (`examples/tinylm`), a fake OpenAI-compatible model that streams token by token, calls tools and comes in personas that loop, hallucinate tools, ignore denials or follow prompt injections; offline and deterministic. `examples/tinylm/check.sh` runs every scenario and checks its exit code, in CI too. An onboarding study records the first install and the rough edges it found.

### Fixed

- Diff-check collection rehashes tracked Git content instead of trusting copied
  index metadata, and applies executable modes portably on BSD/macOS, including
  option-like filenames. Coupled Linux-only sandbox service tests no longer
  break macOS validation.

- **`evalsi compare` no longer crashes** with `KeyError: 'low'` when a metric's difference interval starts or ends at 0 (proto3 JSON leaves zeros out). `Client.compare_runs` fills them in, which also fixes the MCP server's and the training loop's server comparisons, where such a bound read as missing.
- **`evalsi serve --help`** (and `-h`) prints `evalsid serve`'s flags instead of failing with "unrecognized arguments".
- **The trials advisory** no longer recommends millions of trials for a token count: metric summaries carry the evaluator's declared `min` and `max`, a bounded metric's variance bound is capped at what its range allows, the one-line advice under a run considers only bounded metrics and prefers one that varied when bounds tie, and `evalsi determinism` marks each metric `bounded`.
- **Piping the CLI into `head`** ends quietly with exit 141 instead of a `BrokenPipeError` traceback. Buffered output is flushed before returning, including short summaries that previously failed only during interpreter shutdown.
- **The metrics table** says `(lower is better)` beside such metrics (embedded runs; a server's summaries do not carry the direction yet) and leaves out metrics no record produced, skipped or errored on, such as a pass/fail checker's empty `task-score`; the JSON keeps them. `evalsi matrix` prints its `*` footnote only when a row has a star.
- **`evalsi doctor`** shows each sandbox backend's isolation level (`bwrap (namespaced), landlock (confined)`), so agent readiness leaving out a confined backend is explained.
- **The web UI's compare page** no longer colours a significant difference as pass or fail, since it does not know which direction each metric prefers; it says "(higher)" or "(lower)".
- **Docs:** `network: deny` leaves no egress policy events (use `allowlist` to observe attempts); the approval-gate example anchors its command globs (`*git push*`), since `git push*` let `sh -c 'git push ...'` run; fork logs are named `<task>.<trial>.<fork_as>.jsonl`; the README's server section names `datasets_dir`.
- A keyed dataset upload is validated from its spool file instead of being written to disk twice and taking two upload slots.
- Scheduled windows list again after a short page and ask again for traces a store listed but did not return; runs are labelled `incomplete_traces` or `listing_unstable`.
- `COPY file .` in an imported Dockerfile made a file named after the directory instead of copying into it.

### Changed

## [0.3.1] - 2026-10-22

### Upgrade notes

These come from the 22 October deep review ([bug report](docs/reviews/2026-10-22-deep-review/bug-report.md)) and can break existing setups:

- **Local image refs are refused by default.** `dir:`, `oci-layout:` and `docker-archive:` images (including with `evalsid sandbox run`) now need `sandbox.allow_local_images: true`, because a spec could name `dir:/` and read the daemon user's files. With `image_signatures` configured, its `allow_local` still decides.
- **Strict JSON requests.** REST and Connect-JSON requests with unknown fields or enum values now get 400 `InvalidArgument` instead of having them silently dropped, and unknown query parameters get 400 instead of 500. A client that sends fields this server does not know breaks; upgrade clients and server together. Responses are unchanged.
- **Tokens need `exp`.** A non-empty `required_claims` used to replace the default `exp` requirement; `exp` is now always required and `required_claims` adds to it.
- **DeepEval toxicity, bias and hallucination are higher-is-better**, matching deepeval 4.2.8 (1 = pass). Flip gates and comparisons on these metrics.
- Re-scoring a trace overwrites its Langfuse score instead of adding a second one.
- An unknown project returns `PermissionDenied` (was `InvalidArgument`), and a rate-limited or busy dataset upload returns 429 with `Retry-After` (was 413).
- `evalsi eval` exits 1 when every evaluation errored, as `evalsi run` does.
- Krippendorff alpha clusters keep types apart: the string `"1"`, the number `1` and `True` are now different values.

### Added

- The 21 October AKS and live-Claude [verification reports](docs/verification/AKS-FOLLOWUP-2026-10-21.md) and their [fixtures](tests/verification/README.md), with the open items they leave listed in [LEFTOVERS](docs/LEFTOVERS.md).
- **Approval gates for the built-in agent.** The `evalsi_harness.approval:ApprovalGate` hook applies allow/ask/deny rules by tool, path and command, answers each `ask` from a scripted approver (approve, edit, deny or no-answer), and records `hitl_request` and `hitl_resolved` steps that replay exactly. New `denial-respected` and `approval-coverage` evaluators in the `agent` pack score what happens after a denial and whether sensitive calls were approved. Hooks can now emit steps with `ctx.emit`. The approver is scripted; a model or human approver and an agent-initiated request are not built.
- [The built-in agent harness](docs/guides/built-in-harness.md): one page listing what `evalsi-harness` provides and what is not built, and a refreshed `evalsi-harness` README. The [harness roadmap](docs/HARNESS-ROADMAP.md) gains H8 (approval gates and human-in-the-loop events, deeper multi-agent topologies, richer conversation evaluation), proposed and unbuilt.
- [Pre-0.4 release plan](docs/PRE-0.4-RELEASE-PLAN.md): the product-readiness criteria for stable 0.4, an interim-release path, and customer-validation criteria (pilots, retention, willingness to pay) that gate calling the project beta rather than 0.4.
- **Evaluator validation and judge calibration.** `evalsi calibrate freeze|run|verify|report|compare` and the Python SDK freeze individual human pass/fail ratings from explicit records or existing annotation exports, isolate tuning from held-out scoring (including tool-only conversation inputs), compare evaluator/prompt/model/threshold configurations, and measure false positives/negatives, agreement, slices and fresh-call repeatability. Reports pin records, labels, source/configuration and JSON/logprob judge-call hashes and failures, use group-bootstrap uncertainty without counting repeats as independent cases, and distinguish judge drift on fixed outputs from target improvement. Includes an offline synthetic example and real-client/scripted-HTTP controls; deployed judges have not been certified against real human labels.
- **Support and refund starter suite** (`examples/support-refund`, [guide](docs/guides/support-refund-suite.md)): twelve synthetic, editable tasks (authorization, amounts, recipients, duplicate prevention, retry after a timeout, clarification, human handoff) against a small order service, graded on its final state in a clean checker sandbox. A passing stand-in agent and a regressed one show the gate exiting 0 and 3 offline.
- `builtin/state-assertion` turns one named outcome from a checker's per-test results into a metric, so each business rule gets its own gate. An assertion a task does not apply to is skipped, never passed.
- **Browser release workbench:** configure recorded/model/HTTP-agent runs on approved catalog suites, choose evaluators/judges/trials/token budgets, validate and review destinations before execution, and build reviewed release policies through forms. Explicit baselines, immutable decision IDs and new-attempt controls preserve existing release semantics. Export pinned candidate specs, policies, CLI commands and Action steps.
- **Paired case inspector:** direct record/trial links from run and release results show model/tool events, arguments/results, stop reasons, checker outcomes and evaluator explanations. `RunService.GetRecordEvidence` (`GET /v1alpha1/runs/{run_id}/record?record_id=&trial=`) reads exact evidence with run permissions; `ListRunResults.records_by_trial` adds unambiguous trial associations while retaining existing clients.

- `storage.sqlite.synchronous: normal` opts the default SQLite database into `PRAGMA synchronous=NORMAL`: faster writes, but a power loss can drop the last commits (WAL mode never corrupts). The default stays `full`.
- `sandbox.firecracker.max_parallel_boots` (chart: `firecracker.maxParallelBoots`) limits concurrent cold microVM boots; default 8.
- **Strict audit mode** (decision 0026). `audit.mode: strict`, the default when authentication is on, writes a change's audit entry before the change and refuses the call (`unavailable`) when the entry cannot be written. Automatic run deletes and archives skip runs they cannot audit. `besteffort` keeps the previous behaviour. Failed writes are counted in `evalsi_audit_write_failures_total`.
- **Richer audit entries.** Each entry records how the caller authenticated (method, JWT issuer, `jti` and `kid`, API key name, client certificate fingerprint), the caller's groups, and `subject` and `actor`. `audit.reads` records allowed reads of the listed kinds. The server records `config.load` at startup, and `config.reload` when credential grants or judge projects change.
- **Hash-chained audit log.** Entries carry a sequence number and SHA-256 hashes. `evalsi auth audit verify` (`AuthService.VerifyAuditLog`, `GET /v1alpha1/audit:verify`, owners only) reports the first edited, missing or reordered entry and exits 3 when it finds one.
- **Versioned schema migrations.** Steps are recorded in `schema_migrations` with a minimum reader version, so an older `evalsid` refuses a database a newer release contracted. The expand-then-contract rule is in CONTRIBUTING.
- The [enterprise deployment guide](docs/guides/enterprise-deployment.md) covers topologies, every outbound connection, audit settings, and data lifecycle and erasure.
- Pinned baseline/candidate release decisions connect approved held-out catalog suites to enforced CLI, browser and GitHub Action workflows. Captured evaluator/judge/checker contracts, full record/trial coverage, paired regression bounds, critical cases and usage thresholds prevent incomplete evidence from passing. Saves immutable, source-authorized decision records and portable integrity-checked reports; commit/model identities remain declarations rather than execution attestations.

- **`builtin/run-completed`** passes an agent run that ended `completed`, and fails one stopped for steps, spend or time, failed, or left waiting on a human. Connectors now report why a run stopped instead of always `completed`: an A2A task's last state (`input_required`, `failed`, ...) and an HTTP agent's `stop_reason_path`. A run left at `awaiting_human` previously passed gates on tool errors.
- A gate on a metric every record skipped now says so (`no record was scored (3 skipped, 0 errors)`) instead of `metric has no mean`.
- A shared dataset catalog publishes immutable project/name/version suites from explicit records, portable snapshots or approved failure revisions. Adds digest-bound approval with separate authenticated publishing/reviewing principals, retirement, item/manifest diffs, transactional history and source-aware read permissions. Approved catalog pins load directly into server runs and remain on stored records; browser, CLI and SDK cover publication through regression runs. Initial storage is limited to 2 MiB of content per version, with no erasure API or signature guarantee.

- **HTTP agents report their own trajectory and usage.** `target.agent.http` takes `trajectory_path` (steps in Evals.si record form, so a wrapped agent's tool, handoff and guardrail steps reach the evaluators; a `session_id` there lands in `metadata.agent.session_id`) and `usage_path` (`input_tokens`/`output_tokens`, or `prompt_tokens`/`completion_tokens`, and `cost_usd`), so matrix tokens-per-task is no longer 0 for HTTP agents. `body_template` adds `{{trial}}` and `{{session_id}}`, which is unique per task and trial: `{{task_id}}` is the same in every trial, so an agent that keyed its thread on it carried one trial's history into the next.
- **HTTP agents can stream.** With `stream: true`, `target.agent.http` reads server-sent events: answer, messages and usage from the last event that has them, steps from every event at `trajectory_path`, and with `delta_path` text chunks joined into the answer.
- **A2A over HTTP+JSON.** `target.agent.a2a.binding: HTTP+JSON` speaks A2A 0.3's REST binding (`/v1/message:send`, `/v1/tasks/{id}`, `/v1/message:stream`), for servers that do not offer JSON-RPC.
- **OTLP traces record sub-agent handoffs.** An `invoke_agent` span under a different agent's `invoke_agent` span gets a `handoff` step between them, so `builtin/handoff-correctness` scores traces as it does harness runs.
- A project-scoped production failure inbox captures source trace revisions once, supports assignment and editable/redacted cases, records transactional revision history and approves explicit saved expectations. Adds browser trace/inbox workflows, a synchronous SDK and `evalsi inbox` commands, including approved-revision export directly to digest-pinned snapshots. Optimistic concurrency prevents lost edits; edits revoke approval, and exports recheck current state without replaying cached private responses. Includes a synthetic incident-to-CI demo with passing/failing controls.

- `evalsi dataset overlap` checks independently pinned tuning/held-out snapshots for shared IDs and exact normalized inputs, including renamed cases. Its opt-in CI policy exits 3 on overlap and 1 on incomplete input coverage; reports omit raw payloads and group duplicate inputs without a Cartesian expansion. Includes reproducible clean and deliberately overlapping split controls.
- `evalsi dataset snapshot`, `inspect`, `verify` and `diff` create and review portable named datasets with explicit record IDs, owners, held-out/tuning labels and provenance. The `snapshot://` importer requires an approved SHA-256 pin before local or worker execution; publication is atomic and never overwrites an existing path. This is an initial dataset-lifecycle slice, not a central registry or approval service.
- `scripts/probe-cli-proxy.py` runs a command with the proxy variables the sandbox sets pointed at a logging listener and prints the hosts it asked for, to check that a CLI agent honours the egress allowlist. Codex 0.163.0 and OpenCode 1.19.3 do, and both need more hosts than a one-host allowlist (see the Harness² guide).

- **`builtin/evidence-stage-audit`.** A deterministic funnel for agents that read evidence: required passages retrieved, then held by active evidence the answer cites, then the expected answer present. Each stage is scored only when the one before passed, so its mean is conditional. Needs `evidence_state` and a `{evidence, answer}` reference.
- **`builtin/evidence-stage-judge`.** The same funnel graded by a judge in one call: it reads paraphrase and needs only the expected answer (or `{evidence, answer}`) as the reference. Metrics `judged-evidence-retrieved`, `judged-evidence-kept-and-used`, `judged-answer-from-evidence`, each scored only if the one before passed in the judge's verdict. Tested with a scripted judge only; it is uncalibrated against human labels, and the score metadata flags a clipped transcript.

- **`builtin/rubric-grade`.** A judge grades the final answer against the rubric a `lab://` or `jobbench://` task carries in `metadata.grading.rubric` (a list, or `{"rubrics": [{criterion, weight}]}`) and scores the weighted share of criteria met in one judge call. It sees the answer text only, not files left in the workspace, so it is a stand-in for the benchmarks' graders, and it is uncalibrated against human labels. A record with no rubric is skipped; a rubric of an unknown shape or a judge that misses a criterion is an error.
- **Variance-aware trial recommendation.** With `trials` above 1, `evalsi run` prints how many trials per task the observed within-task variance supports (the largest per-task variance bound: exact binomial for pass/fail, chi-square for numeric) and writes `trial_advice` to `--output`; `evalsi determinism` carries it too. A report only: default trials and gates are unchanged. Server runs get it through `evalsi determinism` on their results.


- **H6 rollouts and environment specs.** `evalsi_harness.rollout` plays task episodes with a model (`rollout`, and `RolloutPool` for many at once over one shared setup), keeping each turn's tool calls, observations, process rewards and tokens. `pool.stop()` pauses running rollouts at a turn boundary with a snapshot and `pool.run(resume=...)` continues them; on a rung that cannot snapshot a stopped rollout is `cancelled` and says so. Cancelling a run destroys every episode's sandbox. `TaskEnv` takes a shared `pool=`, and can `snapshot()` and `restore()` an episode.
- **Step-level rewards.** `evalsi_harness.process`: `TaskEnv(process_rewards=[...])` returns each step's reward in `StepResult.process_reward`, beside the checker's outcome reward. `EvaluatorReward` scores the trajectory so far with any record-scope evaluator (the change in its score, or its level; a judge-backed evaluator costs a call per step), `ToolErrorPenalty` is a fixed penalty. A score that cannot be computed is `None`, not 0.
- **Token IDs and log-probabilities per turn.** `TargetConfig(token_trace=True)` on an `openai-compatible` chat-completions target asks a vLLM server for `prompt_token_ids`, `token_ids` and log-probabilities (`return_token_ids`, `return_tokens_as_token_ids`), also when streaming, and keeps them on `ModelTurn.tokens` and in the cassette. What the server did not return is named in `TokenTrace.missing`. Set from code, not from a run spec (no proto field); written against vLLM's documented fields and a fake server, not a live vLLM or SGLang.
- **Gymnasium and NeMo Gym.** `evalsi_harness.envspecs.gymnasium.TaskGymEnv` is a Gymnasium `Env` (checked with `check_env`), and `envspecs.nemogym.TaskResourcesServer` serves tasks as a NeMo Gym `GymnasiumServer` (`dataset_row` builds the rows). Both run in the `envspecs` CI job against the real packages (`gymnasium` 1.4.0, `nemo-gym` 0.7.0 on Python 3.13). A checker that cannot run raises instead of returning a reward of 0.

- **Clean checker isolation.** `checker.isolation: clean` with `checker.outputs` runs the checker in a fresh sandbox of the same environment that receives only the agent's declared output files, so edited tests, shims on `PATH` and installed packages cannot reach the grader. New `Checker.isolation` and `Checker.outputs` proto fields; the server validates them.
- **`builtin/trial-tampering` reward-hacking signals.** Flags edited tests or protected files, the expected answer added as a literal to non-test code, and tool calls naming hidden checker files. A CLI agent with no trajectory reader is scored on its diff; a record with neither is skipped. With `summary.exclude_flagged_trials`, trials it flags are not credited by `pass@k` and `pass^k` (off by default; local and server summaries agree). The harness now records `metadata.checker_files`.
- **Finer ablation and a cross-task harm check.** `evalsi ablate plan --by unit` writes one revert variant per skill, sub-agent, script or plugin instead of per component, and `evalsi ablate attribute --harm` adds, per edit, the tasks it helped and the tasks it hurt (trials averaged, in the metric's direction), marking an edit that helps some and hurts others as `mixed` even when its average effect is positive or zero. Each edit also gets an exact sign test across the tasks that changed (`sign_p`); it has little power on a few tasks, and nothing here tests a single task's change.
- **`git=true` on `harbor://` and `terminal-bench://`.** Makes the task's workdir a git repository with one baseline commit (skipped when it already is one) so the agent's changes are recorded as a diff and `trial-tampering` can read them. Off by default; needs git in the image.
- **Harness² interop (H7).** `evalsi harness2 import` turns a Harness² run namespace into results files for `evalsi matrix`, and `evalsi harness2 calibrate` reports how often its selection matches the candidate we score highest. `evalsi matrix --gate` fails when a refined harness is significantly worse than base, or worse held-out than tuned. `evalsi ablate plan|attribute` reverts one harness component at a time and attributes the gain. New `agent`-pack evaluators: `harness-edit-weakened-guardrail`, `harness-edit-policy-violation`, `harness-edit-scope`, `harness-edit-mechanism-ran` and `contamination-fetch`. `harbor://` gains `reward=score.json` for WorkBuddy-style verifiers, and `lab://` and `jobbench://` read a directory you supply (no dataset content is shipped). Written from the Harness² source, not from a recorded run; see [the guide](docs/guides/harness2.md).
- `evalsi doctor` checks installed versions, worker dependencies and real sandbox availability. `--require server` and `--require agent` fail when the requested capabilities are missing; plain SDK scoring does not require a sandbox.
- `evalsi init` creates offline recorded-output or sandboxed-agent starter projects, including a working example, a deliberately regressed control, error-rate gates and local report instructions. Existing directories are never overwritten.
- A root composite GitHub Action runs gates with published 0.3.0, writes metrics and identity summaries, optionally compares compatible paired baselines and propagates failures. Raw results/log uploads are opt-in. Added an onboarding guide, website navigation and action positive/negative CI controls; roadmap acceptance criteria remain open beyond these initial slices.

The paper's gains come from one setup, so it is a strategy to compare, not a default.

A modified, deleted or new file under a pattern is a `sandbox.protected_file_modified` guardrail step; with `on_change: fail` (default) the trial fails without running the checker, and with `restore` the originals are written back before it runs. On Anthropic, text after tool results joins the same user turn.
- **`delegate`: sub-agents for the built-in agent (H2).** `tools.builtin: [delegate]` lets the agent hand a subtask to a sub-agent with a clean context and the same tools, up to `delegate_steps` model calls, and keep only its report. Its spend comes out of the parent's budget, its steps are on the trajectory under a `subagent` step, hooks cover it, and it replays with the parent's recording. This is the `offload` context pattern and the first multi-agent trajectory.

- **Session resume and fork for the built-in agent (H2).** A recording is now written as it happens, so a trial that dies leaves its log up to the last step. `recording.mode: resume` replays that log (re-running sandbox commands to rebuild the environment) and continues live, appending to it, and grades the same as an uninterrupted trial; `mode: fork` replays the first `branch_at_step` turns into a new log (`fork_as`) that names its parent, so logs form a tree (`session_tree`). Each decision is a step; a failing hook ends the run with its error. On a server the class must be in `agents.trusted_python`; the server validates the list and the CRD gains it. A recording replays only with the same hooks, tools and context strategy.
- **Optional editing and search tools for the built-in agent (H2).** `tools.builtin` lists extra tools by name: `edit_file`, `glob`, `grep` and `apply_patch`. They are off by default, so the default toolset and existing results are unchanged. They need nothing in the task image beyond `find`, `grep` and `git` or `patch`.

The readable thinking is on the `llm` step. Cassettes are now version 2 (a header line; version 1 files replay unchanged). The server validates the new options and checks each fallback's key against the project's credential grants; the CRD gains the fields. Unit and end-to-end tested over a mock transport and a local server; not run against a live provider.

### Changed

- **Dependencies are scanned for known vulnerabilities, and kept current.** A new `security` workflow runs `govulncheck`, `pip-audit` on the locked Python set and `npm audit` on pull requests, on dependency changes on `main` and weekly, and Dependabot opens grouped weekly updates for Go, Python, npm, Docker and GitHub Actions. The first scan found 41 reachable advisories in Go 1.26.0, the version CI and the release binaries were built with, so `go.mod` now requires Go 1.26.9, and `golang.org/x/net` is raised to v0.60.0 for five HTTP/2 advisories. The review that found these, and the work it left open, are in `docs/LEFTOVERS.md`.

- **A truncated or refused turn no longer reads as a completed run.** A turn cut off by `max_tokens` (or `length`) ends the run as `budget` with an error, instead of running a half-written tool call or reporting `completed`. A `refusal` (also a chat completions `refusal` or `content_filter`) is its own stop reason, and `pause_turn` resumes the turn. HTTP 529 (Anthropic overloaded) is retried. For Anthropic targets, `budget.tokens` now counts cached prompt tokens too, so a spec with a token budget may get fewer steps than before.

- **Evals.si is described as evaluating AI before you ship, while it runs, and as you train it,** with agents as the lead use case and RAG and training alongside. The README, the homepage (a new Agents / RAG / Training section and code tabs), the link-preview card, the `evalsi` and `evalsi-harness` PyPI descriptions and keywords, `evalsi --help` and the site metadata say so. The PyPI text changes with the next release.
- **The site is at https://evalsi.dev/.** The PyPI project links, the READMEs and SUPPORT.md point to it, and the old `abhishek-rnjn.github.io/Evals.si/` address redirects there. The README gains a 30-second `pip install` quickstart and a short comparison with the metric libraries and benchmark harnesses that Evals.si runs as adapters. The PyPI links change with the next release.
- The PyPI pages of `evalsi` and `evalsi-harness` describe the project: what Evals.si does, installs and extras (including the Linux platform wheels), a quickstart, runs and gates, the server client, RL rewards and the evaluator packs, with keywords and classifiers. CI checks that both render (`twine check --strict`). A published version's page cannot change, so this shows from the next release.

### Fixed

- **A response could close its own fence in a judge prompt.** The judge, RAG and agent evaluators and both simulated users put model output, retrieved context, references, trajectories, diffs and conversation text inside tags such as `<response>` and tell the model to treat them as data, but text containing `</response>` ended the fence and could write instructions outside it. The opening `<` of any fence tag in such text is now sent as `&lt;`. A record whose text contains a fence tag reaches the judge escaped, so its score can differ from an earlier run. Near-misses a model could still read as a closing tag are escaped too: whitespace or invisible characters around the slash (`</ response>`, `<​/response>`) and full-width brackets.

- **A NaN score passed every gate.** A gate compared with `<` and `>`, and NaN fails both, so a metric whose mean was NaN passed `min` and `max` alike (in `evalsi eval` and on the server). Gates now fail on a value that is not a finite number, and a NaN or infinite score from an evaluator (a plugin, an adapter, a custom pack) is recorded as that record's error rather than scored. Before, the Python SDK also stopped the whole evaluation with a `ValueError` once a metric had two values and a NaN among them. `ImportRun` refuses non-finite scores, and a gate whose `min` or `max` is not a finite number is refused when the spec is created or loaded (a NaN bound also passed every value).
- **pass@k and pass^k left out trials that errored.** A trial whose target or agent failed (or whose evaluation errored) has no score, and was dropped, so a task that passed once and crashed four times had pass^5 of 1. Such a trial now counts as not passed, and a task that errored in every trial counts as failing. The errored trials are reported once, in the metric's own `errors`. Gates on pass^k can fail where they passed before. The metric's own mean is unchanged: it still excludes errored records and reports them in `errors`.
- **Promotion read an imported run's scores under the wrong evaluators.** `ImportRun` numbered evaluators in the order their results came, while `PromoteResults` reads them in spec order, so a `when` condition and the promoted rows' `run_scores` could name one evaluator's score after another. Results are now stored in spec order, and a result from an evaluator the spec does not name is refused.
- **A NaN `confidence_level` crashed the server.** Range checks written as `level <= 0 || level >= 1` let NaN through to the t quantile, which panics; for a stored run that happened in the run's goroutine and stopped `evalsid`. The checks now refuse NaN, `CreateRun` and `ImportRun` check `spec.summary.confidence_level` up front, and a panic during a run fails that run instead of the server.

## [0.2.0] - 2026-10-13

A minor release: it adds the `CheckpointServer` CRD and new `v1alpha1` RPCs, all additive. The headline changes are the agent harness pieces of M2 (a default policy, `evalsi gate`, `evalsi traces` and policy templates), runs evaluated elsewhere stored on the server (`ImportRun`, `Client.log_run`), Linux platform wheels that bundle `evalsid`, run archiving and retention, server-side slicing, and the Databricks Unity Catalog and SageMaker trace-source variants.

### Upgrading from 0.1.0

- **Apply the new CRD first.** Helm does not upgrade CRDs, so apply `CheckpointServer` before upgrading the charts: `kubectl apply -f deploy/helm/evalsi-crds/crds/evals.si_checkpointservers.yaml` (or from the 0.2.0 `evalsi-crds` chart). Then `helm upgrade` `evalsi-crds` (its aggregated roles and the operator's cluster role gain `checkpointservers`) and then `evalsi`. An operator without the CRD keeps running; only `CheckpointServer` is unavailable.
- **A CPU worker pool may not be empty.** The chart now refuses `workers.pools.cpu.replicas: 0` and a `minReplicas` of 0 for the CPU pool under KEDA. Set at least 1 before upgrading.
- **KEDA with external NATS** needs `keda.natsServerMonitoringEndpoint`; the chart refuses the upgrade without it.
- **Nothing to migrate by hand.** The one schema change is additive (a `quota_sandbox` table), made at server start as every migration is ([operations guide](docs/guides/operations.md)). A zero-downtime upgrade from 0.1.0 is not certified: on EKS an API-only rollout passed after the drain fix, and the full upgrade has not been re-run ([evidence](docs/verification/EKS-2026-10-12.md)).
- **Python:** `evalsi-harness` 0.2.0 pins `evalsi` 0.2.0; upgrade both together.

### Added

- **Runs evaluated elsewhere, stored on the server (PRD E6).** `RunService.ImportRun` (`POST /v1alpha1/runs:import`) and `Client.log_run(result)` store a result evaluated in-process (`evalsi.evaluate()`, an embedded run, a training loop) as a finished run, beside the server's own: the records, results and summaries as sent, the gates checked against the summaries, and `run.finished`/`run.gate_failed` webhooks. It needs `runs.create`. Comparing and promoting work even when the run's evaluators exist only in the client; an imported run cannot be resumed.
- **`evalsi gate`: a deploy gate for one release.** Runs a spec on a server against a candidate (`--target-url`, `--set PATH=VALUE`), waits, and exits 0 on pass, 3 on a failed gate, 1 on an error. The same release retried returns the same run, and the same release with a changed spec is refused (the server's idempotency window). For pipelines that call the API instead of applying an `EvalRun`.
- **`evalsi traces`.** `list`, `get` (a trace's record and scores) and `export`, which writes traces, by labels, policy or time, as dataset records with their scores: regression sets, mapping-profile fixtures, and what to look at when an execution was skipped.
- **Policy templates for an agent harness.** `examples/watch/harness-{default,safety,quality,cost}.yaml` score every production execution that names its workflow: tool errors, loops, latency and tokens; PII and secrets with alerts; a judged sample after cheap checks; cost and steps.
- **Measuring a trace source (M3).** `scripts/measure-trace-source.py` seeds MLflow with 30 days of traces, applies a source, times the backfill and the lag of live traces until scored, and fails over a p95 limit. The kind e2e job runs it.
- **CI against verl, OpenRLHF and Claude Code.** The `rlframeworks` job runs Evals.si rewards through verl 0.9.1's reward managers and OpenRLHF 0.11.2's rollout executor (file and HTTP); the `mcp-agent` job has Claude Code drive `evalsi mcp` when an `ANTHROPIC_API_KEY` secret is set. Both run on `main` and on demand.
- **A gated deploy and a default policy in the demo (M2).** `examples/demo/deploy/deploy.sh` plays an agent harness's deploy step: it stages a release of the research assistant as a candidate (`deepagents.candidate`), runs `research-assistant-gate.yaml` against it, and promotes the release only when the run Succeeds, exiting 3 and leaving production as it was otherwise. `overlays/evalsi-demo.yaml` bootstraps an ingest key, a reader key and a default policy (`studio-default`) that scores every production trace naming its workflow; the demo service labels its traces with its workflow, version and stage. The mock model's `mock-regressed` plays a broken release. The kind e2e job runs both.
- **Operator on the host network.** `operator.hostNetwork` (with `webhookPort`, `metricsPort` and `healthPort`) runs the operator and its admission webhooks on the node's network, for clusters whose API server cannot reach overlay pod IPs (EKS with Calico). The Kubernetes guide covers the choices and the Pod Security cost.
- **Operator-managed checkpoint serving.** A `CheckpointServer` resource (`kubectl get checkpointservers`) has the operator run vLLM for a checkpoint: a Deployment and Service, the endpoint and readiness in the status, optional PVC of checkpoints, LoRA mode and API-key Secret. `evalsi checkpoints watch|eval --serve operator` creates one per checkpoint through `kubectl` and deletes it afterwards. Tested with a fake client and a fake `kubectl`; not yet run on a cluster.
- **Platform wheels that bundle `evalsid`.** From 0.2.0, the release builds `evalsi` wheels for Linux amd64 and arm64 (`py3-none-manylinux_2_17_*`) that carry `evalsid` and the static `bwrap` in `evalsi/_bin`, the same release as the package. `evalsi serve`, code evaluators and Wasm plugins look for `evalsid` in `EVALSID`, then the bundle, then `PATH`; `evalsi evalsid-path` prints the one in use. The pure-Python wheel and sdist remain; `pip install --no-binary evalsi evalsi` builds the pure package. CI builds a platform wheel from the real archive, installs it and runs its sandbox.
- **Task environments as OpenEnv and verifiers environments.** `evalsi_harness.envspecs.openenv` (`TaskOpenEnv`, `create_task_app`) and `evalsi_harness.envspecs.verifiers` (`load_environment`) present the tasks agent runs evaluate as an OpenEnv `Environment` and a verifiers `StatefulToolEnv`, rewarded by the task's checker. Install `openenv-core` or `verifiers` yourself (0.3.x each, the versions CI tests against); there are no extras, so the workspace lock stays small.
- **Run archiving.** `RunService.ArchiveRun` (`POST /v1alpha1/runs/{id}:archive`, `evalsi archive-run`) drops a finished run's records, outputs, results and webhook deliveries and keeps its summary, spec, gates and usage (`Run.archived_at`). `runs.archive_after` and `runs.project_archive_after` do it automatically, hourly, before `runs.retention` deletes. Automatic deletes and archives now write audit events (`system:retention`). Archived runs refuse resume, compare, promote, results and dataset-from-run, and the web UI says so. It needs `runs.delete`.
- **A hosted Wasm plugin.** The default plugin index lists `example/text-checks` (JSON validity, word limit and distinct-output checks, compiled to Wasm), with its manifest and module committed under `plugins/wasm/text-checks`, so `evalsi plugins install example/text-checks` works without building anything. A manifest path in an index is relative to the index. `scripts/publish-wasm-example.sh` rebuilds and re-pins it, and tests fail when the pins drift.
- **Server-side slicing.** `RunService.SliceRuns` (`POST /v1alpha1/runs:slice`) computes a metric per run and per record metadata value on the server, over the runs the caller may read, and returns the rows `evalsi analyze slice` computes after downloading every result. `evalsi analyze slice --server URL --on-server` uses it. Both implementations are checked against one fixture. `analyze query` (SQL) stays on the client.
- **Web UI: annotate and sign in from the browser.** A queue page has an **Annotate** button that takes the next item, asks the queue's questions and submits or skips, with the run's scores hidden unless asked for. When `auth.cli_login` names an identity provider, the sign-in page offers it (authorization code with PKCE; evalsid makes the provider metadata and token requests, keeps no secret or refresh token, and talks only to the configured provider). `auth.cli_login.ui_client_id` names the UI's own public client, and `/.well-known/evalsi-auth` gains `ui_login`.
- **Sandbox-time quotas.** `quotas.default.sandbox_seconds_per_day` (and per-project overrides) caps the seconds of sandboxed work a project's runs may use per UTC day: agent tasks from start to end, and code evaluators that run in the sandbox pool. A project at the quota cannot start runs, and a run that passes it stops with an error, as with the token quotas.
- **Automatic run retention.** `runs.retention` (and `runs.project_retention`, with `"0"` for forever) deletes finished runs older than the age, hourly, exactly as `DeleteRun` does, so the stored-run quota is recovered. Pending and running runs, and runs labelled `evalsi.keep: "true"`, are never deleted.
- **MLflow variants for Databricks Unity Catalog and SageMaker.** A `databricks` source can read Unity Catalog schemas (`catalog.schema` locations on a SQL warehouse) as well as experiments, and can sign in as a service principal (`auth.databricks.client_id`, the credential is its OAuth secret). A `sagemaker` source reads a managed MLflow tracking server or app with AWS Signature Version 4 (`auth.sigv4.arn`, the credential is a JSON object of AWS keys; the server's own AWS identity is never used). Both are built from the pinned client source and tested against derived fixtures; neither has run against a real workspace or tracking server. `variant: azureml` is refused with the reason: Azure ML's MLflow server has no MLflow 3 trace API.
- **Custom evaluator example.** `examples/custom-evaluator` is a tested, installable Python evaluator pack (`acme/valid-citations`) that runs by name through the `evalsi.packs` entry point, and it is listed on the website's examples page.

## [0.1.0] - 2026-10-12

The first public release. Evals.si is a self-hosted evaluation service: one set of evaluators for scoring outputs you have, running a model or agent on a dataset, watching live traces, and rewarding RL training.

### Added

- **Score, Run, Watch, Reward.** Score existing outputs; run a target (model, RAG pipeline or agent) on a dataset with trials, gates and budgets; score live traces with online policies; use the same evaluators as RL rewards and in training-loop hooks (PyTorch, Lightning, Hugging Face Trainer and TRL).
- **Evaluators** with confidence intervals on every mean. Records an evaluator cannot judge are skipped, and evaluator failures are errors, never zeros. There is no default judge model.
- **Agent runs** on sandboxed tasks, including SWE-bench, τ-bench, Terminal-Bench and BFCL, over A2A, MCP, HTTP, an OpenAI Responses API or a CLI.
- **Ingest and trace sources.** OTLP ingest (OTel GenAI, OpenInference, OpenLLMetry, MLflow conventions) with redaction; sources that read MLflow, Phoenix and Langfuse, with score write-back; scheduled batch reports; agent-framework traces from LangGraph, CrewAI, the OpenAI Agents SDK, LlamaIndex and the Claude Agent SDK.
- **Pipeline controls.** JSONL and Parquet dataset upload, idempotent keyed writes, run deletion to recover quotas, and an SDK `evalsi.log()` that batches in the background.
- **Adapters** for lm-evaluation-harness, Inspect AI, RAGAS and DeepEval in isolated environments; custom evaluators as Python functions or sandboxed Wasm modules.
- **Sandboxes** that fail closed: Firecracker microVMs where `/dev/kvm` is usable, else bubblewrap, else Landlock, else hardened pods, never with weaker isolation than asked.
- **Server and tools.** A single `evalsid` binary (Connect, gRPC and REST), a web UI, guardrails, annotation queues, webhooks, MCP tools, authentication and per-project credentials, and the `evalsi` CLI and Python SDK.
- **Kubernetes.** Helm charts (`evalsi`, `evalsi-crds`, `evalsi-sandboxd`), an operator with `EvalRun`, `OnlineEvalPolicy`, `Evaluator` and `SandboxClass` CRDs, and an air-gapped install bundle.
- **Release engineering.** Linux amd64 and arm64 archives, Python distributions, multi-architecture images and OCI charts, signed keylessly with Sigstore, with `scripts/verify-release.sh`.

### Security

- The API bounds every RPC message at 64 MiB, and reads at most 64 KiB of a request whose credential was rejected. Connect reads a unary request whole before authentication runs, so a caller without a valid credential could otherwise make the server buffer a body of any size.
- The operator lets a resource name a project other than its namespace (`evals.si/project`) only from the release's namespace or namespaces mapped with `operator.projectNamespaces`, since it acts through the API as an owner.
- The chart's bundled NATS requires a token, and a NetworkPolicy limits its client port to the release's namespace.
- Trace sources refuse shared address space (100.64.0.0/10, where some clouds serve instance metadata), 0.0.0.0/8 and NAT64 addresses of internal hosts unless listed in `sources.allow_hosts`.

### Known limits

See [docs/LEFTOVERS.md](docs/LEFTOVERS.md) for the full list and [SUPPORT.md](SUPPORT.md) for what has been verified. In particular, EKS and GKE have not been run, and the per-release sandbox-pool NetworkPolicy has not been exercised on a cluster that enforces NetworkPolicy.
