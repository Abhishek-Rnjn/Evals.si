# Changelog

All notable changes to this project are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0, minor versions may make breaking changes to the `v1alpha1` API; they are listed under "Changed".

## [Unreleased]

### Added

- **Clean checker isolation.** `checker.isolation: clean` with `checker.outputs` runs the checker in a fresh sandbox of the same environment that receives only the agent's declared output files, so edited tests, shims on `PATH` and installed packages cannot reach the grader. New `Checker.isolation` and `Checker.outputs` proto fields; the server validates them.
- **`builtin/trial-tampering` reward-hacking signals.** Flags edited tests or protected files, the expected answer added as a literal to non-test code, and tool calls naming hidden checker files. With `summary.exclude_flagged_trials`, trials it flags are not credited by `pass@k` and `pass^k` (off by default; local and server summaries agree). The harness now records `metadata.checker_files`.

## [0.3.0] - 2026-10-19

### Upgrade notes

- Upgrade the server, Python SDK and harness together, and refresh the EvalRun CRD before using prompt-injection fault payloads. Mixed-version rolling upgrades remain unverified.
- Stop old metadata writers before upgrading. Startup automatically backfills archived-run quota markers and creates the durable online-evaluation queue. Previously accepted work that predates the queue requires an explicit source backfill.
- Accepted online work is queued durably; the dispatcher stores traces before their scores. Source streams keep independent policy selections. Replay is at least once and can repeat evaluator calls after a crash; unavailable policies or source runners defer acknowledgement. Source write-back delivery after an in-memory handoff retains its existing semantics.
- Authenticated deployments now apply generous per-caller rate limits by default. Configure `rate_limits` for workloads requiring different limits. The webhook SSRF guard remains opt-in.


### Fixed

- Accepted online traces remain queryable while a policy or source runner is unavailable. Deleting a source lets its accepted work finish locally without write-back. Leadership loss cancels evaluation; lease epochs and revision checks fence trace writes, scores and acknowledgments against stale dispatchers. Publication is ordered once across sources, scores follow their input revision, and ClickHouse retention tombstones suppress delayed inserts.
- Archived runs release `max_stored_runs` quota, including archives in existing databases.
- Accepted online evaluation work survives restarts in a durable queue, preserving source policy selection and redaction.

- Private service names bypass the sandbox's external egress proxy in both
  `NO_PROXY` and `no_proxy`, preserving caller exclusions. HTTP sidecars remain
  reachable when agent networking uses `allow` or `allowlist`.

- **Trial PostgreSQL can select a StorageClass.** `devPostgres.storageClassName` now reaches the database PVC, allowing installation on clusters without a default StorageClass. An empty value retains the existing default-class behavior.

- **One-shot checkpoint watches propagate evaluation failures.** `evalsi checkpoints watch --once` now exits 1 when an attempted base/checkpoint evaluation errors, or 3 on failed gates/regressions, rather than always returning success. Errors take precedence over gate failures; continuous watching and stop-file behavior are unchanged.

- **Native Claude Code traces count their full input tokens.** The ingest profile now includes cache-read and cache-creation tokens, preserves explicit canonical totals without double counting, and fills missing input/output counters independently. Real EKS traces exposed a total of six uncached tokens being mistaken for the complete prompt usage.

- **CLI-agent startup and timeout diagnostics survive structured-output parsing.** When a CLI exits or times out before emitting recognizable events, the harness reports its bounded process error instead of incorrectly suggesting an output-format mismatch.

- **Checkpoint servers load the requested model in the stock vLLM image.** The operator now explicitly runs `vllm serve` by default, while preserving `spec.command` overrides. The stock v0.11.0 image's API-server entrypoint accepted the positional model as `model_tag` but loaded its default model instead. **Upgrade note:** existing CheckpointServers roll to the new pod template; one whose image relies on its own entrypoint (a wrapper script, or no `vllm` on `PATH`) must set `spec.command` to that entrypoint.

- **Per-trial services tolerate transient faults without losing results.** A single slow readiness probe no longer fails a command (three misses are needed); service status reads retry API errors and outlive a cancelled caller, so a finished command keeps its real exit code; a healthy check is reused briefly by the next command's pre-check, halving status reads. The start timeout grows by each service's startup-probe budget, a NetworkPolicy canary that could not run is retried (at most every 30 s) instead of refusing services until restart, and `Stats` returns egress and usage even when service status is unavailable. Only `evalsid sandbox serve` reaps a previous server's service pods, so a one-shot command in the pool pod cannot delete live trials' services. Imported multi-service Terminal-Bench tasks get a service lifetime that outlasts their agent and test limits. MCP session cleanup no longer raises when a token refresh fails, and the browser tests install their CSP listener before navigating.

It shares activity rules with `evalsi matrix --mechanisms`; configuration alone does not pass, missing context evidence is skipped, and the score can gate a run.

- **A guide and runnable example for evaluating a RAG pipeline** (`docs/guides/evaluate-rag.md`, `examples/rag`). It scores a pipeline's recorded answers: `citation-accuracy` with no judge, the retrieval metrics (`context-precision`, `context-recall`) and the generation metrics (`faithfulness`, `answer-relevance`) with one, how to read them together, and a CI gate that exits 3 on a bad citation. CI runs the example.
- **A guide and runnable example for gating an agent in CI** (`docs/guides/gate-an-agent-in-ci.md`, `examples/agent-gate`). A stand-in agent runs on two tasks in a sandbox with a hidden checker, the gate passes (exit 0), a regressed copy fails it (exit 3), and a GitHub Actions workflow runs it on pull requests. It needs only `pip install evalsi evalsi-harness` and no API key. CI runs the example, so it stays working.
- **More of DeepEval in the `deepeval` adapter (30 metrics, up from 12).** Agent trace metrics (`task-completion`, `step-efficiency`, `plan-quality`, `plan-adherence`) read the trajectory as a DeepEval trace. Conversational metrics (`knowledge-retention`, `conversation-completeness`, `turn-relevancy`, `role-adherence`, `topic-adherence`, `goal-accuracy`, `conversational-g-eval`) read the record's chat messages. Safety and instruction metrics: `pii-leakage`, `misuse`, `non-advice`, `role-violation`, `prompt-alignment`. **`jev-eval`** and **`conversational-jev-eval`** port DeepEval's JevEval: weighted true/false, scale and choice questions, answered with probabilities by the run's judge rather than TypeSafe's hosted Jev, so no TypeSafe key is read. The same judge serves the `hybrid` and `system_one` eval modes through the new `eval_mode` param. `g-eval` can judge the whole trajectory (`evaluation_params: [trace]`) and `tools_called`.
- **Decisions read off token logprobs, for a Jev-style decider you host.** With `decisions: logprobs`, JevEval's questions and the built-in DeepEval metrics' System One modes take their probabilities from the judge's first-token logprobs over lettered answers, not from probabilities the judge states. This works with any OpenAI-compatible server that returns logprobs (vLLM, SGLang, Ollama, OpenAI). The SDK gains `JudgeClient.next_token_logprobs` (cached and rate-limited like other judge calls), `JudgeSession.label_probabilities`, and a `logprobs` option on `evalsi.testing.scripted_judge`. Judges without logprobs (Claude) fail fast with a configuration error.
- **A DeepEval and JevEval guide** (`docs/guides/deepeval.md`, on the site under Guides). It covers every metric, how records map onto DeepEval's test cases, traces and conversations, writing JevEval questions for RAG and agents, `stated` versus `logprobs` decisions, and running a decider on vLLM, SGLang or Ollama. The README, the PyPI page, the end-to-end guide and the landing page link to it.

- **An error-rate gate.** `stat: GATE_STAT_ERROR_RATE` checks the fraction of a metric's evaluations that errored (`errors / (n + errors)`, skips left out), for example `{metric: task-success, stat: GATE_STAT_ERROR_RATE, max: 0.05}`. A metric's mean leaves errored records out, so this is the gate that fails an agent that crashes on most tasks and passes the rest. It works wherever gates do: run specs run with `evalsi run` (embedded or on a server) and `evalsi gate`, `EvalRun` resources and imported runs. A gate with a stat the server does not know is now refused (before, it was checked as the mean). `GateStat` gains `GATE_STAT_ERROR_RATE` (`v1alpha1`, additive).

- **A LangSmith trace source.** `connector: langsmith` reads a LangSmith project's traces (cloud, EU or self-hosted; history included), scores them with the project's online policies, and writes the scores back as feedback on each trace's root run, updated in place when a score changes. `locations` names tracing projects by name or ID; the credential is an API key, or `<workspace ID>:<API key>`. Built from the pinned `langsmith` 0.4.37 client and tested against fixtures in its shapes, not yet against a live LangSmith. See [trace sources](docs/guides/trace-sources.md#langsmith).

- **Frontier-model handling in the built-in agent (first part of H1).** Anthropic `thinking` and `redacted_thinking` blocks are kept, with their signatures, and sent back before the tool use on the next turn. The Anthropic client puts cache breakpoints on the system prompt, the last tool and the end of the conversation, and records cache-read and cache-write tokens (also on `usage` for chat completions' `cached_tokens`); `input_tokens` is now the whole prompt, and `max_usd` prices cached tokens (a tenth for reads and 1.25 times for writes on Anthropic, full price elsewhere, so a budget stays an upper bound). Retries honour `retry-after` (capped at 60 s) with jitter. Cassettes record thinking and cache tokens; old ones still replay.

- **Context management for long agent runs (first part of H2).** `harness.builtin.context` takes a `strategy` (`none`, `clear-tool-results`, `compact`), the model's `window_tokens`, `trigger` and `target` fractions, and `spill_outputs`. Old tool results are replaced by stubs in batches, and `compact` then summarizes earlier turns with the agent's model; each is a step on the trajectory with before and after token counts, and the run's `agent.context` metadata totals them. The prompt size is the model's last report scaled by characters. A recording replays only under the strategy and window it was recorded with. The default is `none`, so existing specs and cassettes are unchanged. The server validates the fields and the CRD gains them. Tested with a fake model that has a real 200k-token window: a 300-step run overflows it without a strategy and finishes under each of the two.
- **Code mode (H2).** `tools.builtin: [code_mode]` gives the model one tool, `run_code`: it writes a short Python script that calls the task's tools as functions and prints only what it needs. The script runs in a restricted interpreter inside the harness (no `open`, `eval`, `getattr`, `str.format`, classes, regular expressions or imports beyond `json`, with caps on operations, tool calls, the size of every value and output, checked before a result is built), not on the worker's Python. Each tool call a script makes is a step under the `run_code` step, hooks apply to it, and it is recorded and replayed.
- **MCP client upgrades and `tool_search` (H2).** MCP servers take `timeout_s` and per-tool `tool_timeout_s`, `resources` and `prompts` (offered as tools), `elicitation` (the server may ask the user a question mid-call, answered by the simulated user) and `oauth` (client credentials, refreshed on a 401; the two variables need a credential grant for both the token endpoint and the server's URL). Images and audio come back as a note instead of base64, resource links as their uri, and structured output with its `outputSchema` in the tool's description. HTTP replies are read as a stream, so a server can ask a question in the middle of a call. `tools.builtin: [tool_search]` starts the MCP tools unloaded and loads the best matches when the agent searches, keeping hundreds of schemas out of every prompt.
- **`evidence-state` context strategy (H2), after LongHarness.** The agent keeps an evidence list (statement, source, and a quote that must appear in something it read) and a conclusion list (claims, support, open gaps) in an `evidence` tool; corrections supersede or retract instead of appending. The state is sent with every call and is what carries over when the conversation is cut down to the task and the latest turns. The paper's gains come from one setup, so it is a strategy to compare, not a default.
- **`fresh-rounds` context strategy (H2).** `context.strategy: fresh-rounds` runs the task as up to `rounds` rounds, each a new agent with a clean context that starts from the task and the notes it kept in `progress.md`; the run ends when a reply carries `TASK_COMPLETE`. `round_steps` caps a round. Every fresh start is a `context:round` step, and a recording replays only with the same rounds.
- **CLI trajectory readers (H3).** `output_format` on a CLI agent now reads `claude-stream-json` (Claude Code), `codex-json` (`codex exec --json`), `gemini-json` and `pi-json` as well as `dsh-json`, into model-call and tool-call steps with token counts and, where the CLI reports it, the run's cost. Claude Code's sub-agent messages hang under the tool step that started them. A stream with none of the format's events is an error on the run, and the server refuses an unknown format. The fixtures are written to each CLI's documented schema, not captured from a real run (see `docs/LEFTOVERS.md`).
- **Harness profiles, a harness-by-model matrix and the agent's own setup (H3).** `harness.builtin.profile` selects a versioned profile of the built-in agent: `minimal` (a short prompt and four tools, no escalation tool), `standard` (the H2 toolset, compacting when a window is given) or `code-mode`; `name@N` pins a version, the run records it, and a recording replays only under the same profile. `evalsi matrix a.json b.json --metric M` lays results files out as cells with the score and interval, model calls, tokens and dollars per task and the score per thousand tokens, a paired difference from the first cell with its interval, a tuned/held-out split with `--tuned-on`, and `--mechanisms`, a mechanism-ran check that shows which offered tools and context strategy ran in how many tasks (the run's metadata gains `tools_offered`). `environment.files` carries `AGENTS.md`, skills and MCP configs into the sandbox as part of the task (documented, and tested for CLI agents).
- **A2A streaming (H3).** `a2a.stream: true` uses `message/stream` instead of `message/send` and polling: each task state and status message is a step (`a2a:working`, `a2a:input-required`, ...), artifact chunks are joined, an `input-required` task continues in the same context, and a stream that ends before the task settles is an error, not an answer. Tested against a local server; push notifications are not used.
- **Protected files for the checker (H4).** `environment.checker.protect` lists globs (relative to the workdir) of files the agent must not change, hashed when each trial starts and compared before the checker runs. A modified, deleted or new file under a pattern is a `sandbox.protected_file_modified` guardrail step; with `on_change: fail` (default) the trial fails without running the checker, and with `restore` the originals are written back before it runs. Workdir only; running the checker from a clean snapshot copy is not built.
- **Mid-run user messages (H4).** `harness.builtin.interjections` (`[{at_step, message}]`) delivers scripted user messages while the built-in agent works: one is added after the agent's `at_step`-th model call (and before it may finish), recorded as a `user-interjection` step, kept in view under every context strategy, and part of a recording's guard. On Anthropic, text after tool results joins the same user turn.
- **`delegate`: sub-agents for the built-in agent (H2).** `tools.builtin: [delegate]` lets the agent hand a subtask to a sub-agent with a clean context and the same tools, up to `delegate_steps` model calls, and keep only its report. Its spend comes out of the parent's budget, its steps are on the trajectory under a `subagent` step, hooks cover it, and it replays with the parent's recording. This is the `offload` context pattern and the first multi-agent trajectory.
- **`session_search` and `memory` for the built-in agent (H2).** `tools.builtin` also takes `session_search`, which searches the run's unabridged history (what clearing and compaction removed) for some text and reads an entry back in full, and `memory`, notes under `.evalsi-memory/` that survive context management and are rebuilt on replay.
- **Session resume and fork for the built-in agent (H2).** A recording is now written as it happens, so a trial that dies leaves its log up to the last step. `recording.mode: resume` replays that log (re-running sandbox commands to rebuild the environment) and continues live, appending to it, and grades the same as an uninterrupted trial; `mode: fork` replays the first `branch_at_step` turns into a new log (`fork_as`) that names its parent, so logs form a tree (`session_tree`). Entries carry `id` and `parent`. The server validates the modes and the fork name; the CRD gains `fork_as`.
- **Hooks for the built-in agent (H2).** `harness.builtin.hooks` lists Python classes with `before_model`, `before_tool`, `after_tool`, `on_compaction` and `on_stop` methods: change a call's prompt, deny or rewrite a tool call, replace a result, or send the agent back to work once it thinks it is done. Each decision is a step; a failing hook ends the run with its error. On a server the class must be in `agents.trusted_python`; the server validates the list and the CRD gains it. A recording replays only with the same hooks, tools and context strategy.
- **Optional editing and search tools for the built-in agent (H2).** `tools.builtin` lists extra tools by name: `edit_file`, `glob`, `grep` and `apply_patch`. They are off by default, so the default toolset and existing results are unchanged. They need nothing in the task image beyond `find`, `grep` and `git` or `patch`.
- **The rest of H1 for the built-in agent.** The target takes `thinking` (adaptive, enabled with a budget, or disabled; Anthropic), `api: responses` (the OpenAI Responses API, stateless, with encrypted reasoning items carried between turns and reasoning tokens counted), `stream` (server-sent events for Anthropic, chat completions and Responses), `max_concurrency` (a per-endpoint limit on concurrent model calls) and `fallbacks` with `fallback_after` (switch models after repeated failures; the switch is recorded on the step and reasoning blocks from another model are dropped). A turn cut off by `max_tokens` is now retried once with twice the limit (up to 128k) by default, which spends extra tokens; if the provider refuses the higher limit, the run ends as `budget` as before. The readable thinking is on the `llm` step. Cassettes are now version 2 (a header line; version 1 files replay unchanged). The server validates the new options and checks each fallback's key against the project's credential grants; the CRD gains the fields. Unit and end-to-end tested over a mock transport and a local server; not run against a live provider.

### Changed

- **Dependencies are scanned for known vulnerabilities, and kept current.** A new `security` workflow runs `govulncheck`, `pip-audit` on the locked Python set and `npm audit` on pull requests, on dependency changes on `main` and weekly, and Dependabot opens grouped weekly updates for Go, Python, npm, Docker and GitHub Actions. For Anthropic targets, `budget.tokens` now counts cached prompt tokens too, so a spec with a token budget may get fewer steps than before.

### Fixed

- **A response could close its own fence in a judge prompt.** The judge, RAG and agent evaluators and both simulated users put model output, retrieved context, references, trajectories, diffs and conversation text inside tags such as `<response>` and tell the model to treat them as data, but text containing `</response>` ended the fence and could write instructions outside it. The opening `<` of any fence tag in such text is now sent as `&lt;`. A record whose text contains a fence tag reaches the judge escaped, so its score can differ from an earlier run. Near-misses a model could still read as a closing tag are escaped too: whitespace or invisible characters around the slash (`</ response>`, `<​/response>`) and full-width brackets.

- **A NaN score passed every gate.** A gate compared with `<` and `>`, and NaN fails both, so a metric whose mean was NaN passed `min` and `max` alike (in `evalsi eval` and on the server). Gates now fail on a value that is not a finite number, and a NaN or infinite score from an evaluator (a plugin, an adapter, a custom pack) is recorded as that record's error rather than scored. Before, the Python SDK also stopped the whole evaluation with a `ValueError` once a metric had two values and a NaN among them. `ImportRun` refuses non-finite scores, and a gate whose `min` or `max` is not a finite number is refused when the spec is created or loaded (a NaN bound also passed every value).
- **pass@k and pass^k left out trials that errored.** A trial whose target or agent failed (or whose evaluation errored) has no score, and was dropped, so a task that passed once and crashed four times had pass^5 of 1. Such a trial now counts as not passed, and a task that errored in every trial counts as failing. The errored trials are reported once, in the metric's own `errors`. Gates on pass^k can fail where they passed before. The metric's own mean is unchanged: it still excludes errored records and reports them in `errors`.
- **Promotion read an imported run's scores under the wrong evaluators.** `ImportRun` numbered evaluators in the order their results came, while `PromoteResults` reads them in spec order, so a `when` condition and the promoted rows' `run_scores` could name one evaluator's score after another. Results are now stored in spec order, and a result from an evaluator the spec does not name is refused.
- **A NaN `confidence_level` crashed the server.** Range checks written as `level <= 0 || level >= 1` let NaN through to the t quantile, which panics; for a stored run that happened in the run's goroutine and stopped `evalsid`. The checks now refuse NaN, `CreateRun` and `ImportRun` check `spec.summary.confidence_level` up front, and a panic during a run fails that run instead of the server.

## [0.2.0] - 2026-10-13

A minor release: it adds the `CheckpointServer` CRD and new `v1alpha1` RPCs, all additive. The headline changes are the agent harness pieces of M2 (a default policy, `evalsi gate`, `evalsi traces` and policy templates), runs evaluated elsewhere stored on the server (`ImportRun`, `Client.log_run`), Linux platform wheels that bundle `evalsid`, run archiving and retention, server-side slicing, and the Databricks Unity Catalog and SageMaker trace-source variants.

### Upgrading from 0.1.0

- **Apply the new CRD first.** Helm does not upgrade CRDs, so apply `CheckpointServer` before upgrading the charts: `kubectl apply -f deploy/helm/evalsi-crds/crds/evals.si_checkpointservers.yaml` (or from the 0.2.0 `evalsi-crds` chart). Then `helm upgrade` `evalsi-crds` (its aggregated roles and the operator's cluster role gain `checkpointservers`) and then `evalsi`. An operator without the CRD keeps running; only `CheckpointServer` is unavailable.
- **A CPU worker pool may not be empty.** The chart now refuses `workers.pools.cpu.replicas: 0` and a `minReplicas` of 0 for the CPU pool under KEDA. Set at least 1 before upgrading.
- **KEDA with external NATS** needs `keda.natsServerMonitoringEndpoint`; the chart refuses the upgrade without it.
- **Nothing to migrate by hand.** The one schema change is additive (a `quota_sandbox` table), made at server start as every migration is ([operations guide](docs/guides/operations.md)). A zero-downtime upgrade from 0.1.0 is not certified: on EKS an API-only rollout passed after the drain fix, and the full upgrade has not been re-run ([evidence](docs/verification/EKS-2026-10-12.md)).
- **Python:** `evalsi-harness` 0.2.0 pins `evalsi` 0.2.0; upgrade both together.

### Added

- **Runs evaluated elsewhere, stored on the server (PRD E6).** `RunService.ImportRun` (`POST /v1alpha1/runs:import`) and `Client.log_run(result)` store a result evaluated in-process (`evalsi.evaluate()`, an embedded run, a training loop) as a finished run, beside the server's own: the records, results and summaries as sent, the gates checked against the summaries, and `run.finished`/`run.gate_failed` webhooks. It needs `runs.create`. Comparing and promoting work even when the run's evaluators exist only in the client; an imported run cannot be resumed.
- **`evalsi gate`: a deploy gate for one release.** Runs a spec on a server against a candidate (`--target-url`, `--set PATH=VALUE`), waits, and exits 0 on pass, 3 on a failed gate, 1 on an error. The same release retried returns the same run, and the same release with a changed spec is refused (the server's idempotency window). For pipelines that call the API instead of applying an `EvalRun`.
- **`evalsi traces`.** `list`, `get` (a trace's record and scores) and `export`, which writes traces, by labels, policy or time, as dataset records with their scores: regression sets, mapping-profile fixtures, and what to look at when an execution was skipped.
- **Policy templates for an agent harness.** `examples/watch/harness-{default,safety,quality,cost}.yaml` score every production execution that names its workflow: tool errors, loops, latency and tokens; PII and secrets with alerts; a judged sample after cheap checks; cost and steps.
- **Measuring a trace source (M3).** `scripts/measure-trace-source.py` seeds MLflow with 30 days of traces, applies a source, times the backfill and the lag of live traces until scored, and fails over a p95 limit. The kind e2e job runs it.
- **CI against verl, OpenRLHF and Claude Code.** The `rlframeworks` job runs Evals.si rewards through verl 0.9.1's reward managers and OpenRLHF 0.11.2's rollout executor (file and HTTP); the `mcp-agent` job has Claude Code drive `evalsi mcp` when an `ANTHROPIC_API_KEY` secret is set. Both run on `main` and on demand.
- **A gated deploy and a default policy in the demo (M2).** `examples/demo/deploy/deploy.sh` plays an agent harness's deploy step: it stages a release of the research assistant as a candidate (`deepagents.candidate`), runs `research-assistant-gate.yaml` against it, and promotes the release only when the run Succeeds, exiting 3 and leaving production as it was otherwise. `overlays/evalsi-demo.yaml` bootstraps an ingest key, a reader key and a default policy (`studio-default`) that scores every production trace naming its workflow; the demo service labels its traces with its workflow, version and stage. The mock model's `mock-regressed` plays a broken release. The kind e2e job runs both.
- **Operator on the host network.** `operator.hostNetwork` (with `webhookPort`, `metricsPort` and `healthPort`) runs the operator and its admission webhooks on the node's network, for clusters whose API server cannot reach overlay pod IPs (EKS with Calico). The Kubernetes guide covers the choices and the Pod Security cost.
- **Operator-managed checkpoint serving.** A `CheckpointServer` resource (`kubectl get checkpointservers`) has the operator run vLLM for a checkpoint: a Deployment and Service, the endpoint and readiness in the status, optional PVC of checkpoints, LoRA mode and API-key Secret. `evalsi checkpoints watch|eval --serve operator` creates one per checkpoint through `kubectl` and deletes it afterwards. Tested with a fake client and a fake `kubectl`; not yet run on a cluster.
- **Platform wheels that bundle `evalsid`.** From 0.2.0, the release builds `evalsi` wheels for Linux amd64 and arm64 (`py3-none-manylinux_2_17_*`) that carry `evalsid` and the static `bwrap` in `evalsi/_bin`, the same release as the package. `evalsi serve`, code evaluators and Wasm plugins look for `evalsid` in `EVALSID`, then the bundle, then `PATH`; `evalsi evalsid-path` prints the one in use. The pure-Python wheel and sdist remain; `pip install --no-binary evalsi evalsi` builds the pure package. CI builds a platform wheel from the real archive, installs it and runs its sandbox.
- **Task environments as OpenEnv and verifiers environments.** `evalsi_harness.envspecs.openenv` (`TaskOpenEnv`, `create_task_app`) and `evalsi_harness.envspecs.verifiers` (`load_environment`) present the tasks agent runs evaluate as an OpenEnv `Environment` and a verifiers `StatefulToolEnv`, rewarded by the task's checker. Install `openenv-core` or `verifiers` yourself (0.3.x each, the versions CI tests against); there are no extras, so the workspace lock stays small.
- **Run archiving.** `RunService.ArchiveRun` (`POST /v1alpha1/runs/{id}:archive`, `evalsi archive-run`) drops a finished run's records, outputs, results and webhook deliveries and keeps its summary, spec, gates and usage (`Run.archived_at`). `runs.archive_after` and `runs.project_archive_after` do it automatically, hourly, before `runs.retention` deletes. Automatic deletes and archives now write audit events (`system:retention`). Archived runs refuse resume, compare, promote, results and dataset-from-run, and the web UI says so. It needs `runs.delete`.
- **A hosted Wasm plugin.** The default plugin index lists `example/text-checks` (JSON validity, word limit and distinct-output checks, compiled to Wasm), with its manifest and module committed under `plugins/wasm/text-checks`, so `evalsi plugins install example/text-checks` works without building anything. A manifest path in an index is relative to the index. `scripts/publish-wasm-example.sh` rebuilds and re-pins it, and tests fail when the pins drift.
- **Server-side slicing.** `RunService.SliceRuns` (`POST /v1alpha1/runs:slice`) computes a metric per run and per record metadata value on the server, over the runs the caller may read, and returns the rows `evalsi analyze slice` computes after downloading every result. `evalsi analyze slice --server URL --on-server` uses it. Both implementations are checked against one fixture. `analyze query` (SQL) stays on the client.
- **Web UI: annotate and sign in from the browser.** A queue page has an **Annotate** button that takes the next item, asks the queue's questions and submits or skips, with the run's scores hidden unless asked for. When `auth.cli_login` names an identity provider, the sign-in page offers it (authorization code with PKCE; evalsid makes the provider metadata and token requests, keeps no secret or refresh token, and talks only to the configured provider). `auth.cli_login.ui_client_id` names the UI's own public client, and `/.well-known/evalsi-auth` gains `ui_login`.
- **Sandbox-time quotas.** `quotas.default.sandbox_seconds_per_day` (and per-project overrides) caps the seconds of sandboxed work a project's runs may use per UTC day: agent tasks from start to end, and code evaluators that run in the sandbox pool. A project at the quota cannot start runs, and a run that passes it stops with an error, as with the token quotas.
- **Automatic run retention.** `runs.retention` (and `runs.project_retention`, with `"0"` for forever) deletes finished runs older than the age, hourly, exactly as `DeleteRun` does, so the stored-run quota is recovered. Pending and running runs, and runs labelled `evalsi.keep: "true"`, are never deleted.
- **MLflow variants for Databricks Unity Catalog and SageMaker.** A `databricks` source can read Unity Catalog schemas (`catalog.schema` locations on a SQL warehouse) as well as experiments, and can sign in as a service principal (`auth.databricks.client_id`, the credential is its OAuth secret). A `sagemaker` source reads a managed MLflow tracking server or app with AWS Signature Version 4 (`auth.sigv4.arn`, the credential is a JSON object of AWS keys; the server's own AWS identity is never used). Both are built from the pinned client source and tested against derived fixtures; neither has run against a real workspace or tracking server. `variant: azureml` is refused with the reason: Azure ML's MLflow server has no MLflow 3 trace API.
- **Custom evaluator example.** `examples/custom-evaluator` is a tested, installable Python evaluator pack (`acme/valid-citations`) that runs by name through the `evalsi.packs` entry point, and it is listed on the website's examples page.

## [0.1.0] - 2026-10-12

The first public release. Evals.si is a self-hosted evaluation service: one set of evaluators for scoring outputs you have, running a model or agent on a dataset, watching live traces, and rewarding RL training.

### Added

- **Score, Run, Watch, Reward.** Score existing outputs; run a target (model, RAG pipeline or agent) on a dataset with trials, gates and budgets; score live traces with online policies; use the same evaluators as RL rewards and in training-loop hooks (PyTorch, Lightning, Hugging Face Trainer and TRL).
- **Evaluators** with confidence intervals on every mean. Records an evaluator cannot judge are skipped, and evaluator failures are errors, never zeros. There is no default judge model.
- **Agent runs** on sandboxed tasks, including SWE-bench, τ-bench, Terminal-Bench and BFCL, over A2A, MCP, HTTP, an OpenAI Responses API or a CLI.
- **Ingest and trace sources.** OTLP ingest (OTel GenAI, OpenInference, OpenLLMetry, MLflow conventions) with redaction; sources that read MLflow, Phoenix and Langfuse, with score write-back; scheduled batch reports; agent-framework traces from LangGraph, CrewAI, the OpenAI Agents SDK, LlamaIndex and the Claude Agent SDK.
- **Pipeline controls.** JSONL and Parquet dataset upload, idempotent keyed writes, run deletion to recover quotas, and an SDK `evalsi.log()` that batches in the background.
- **Adapters** for lm-evaluation-harness, Inspect AI, RAGAS and DeepEval in isolated environments; custom evaluators as Python functions or sandboxed Wasm modules.
- **Sandboxes** that fail closed: Firecracker microVMs where `/dev/kvm` is usable, else bubblewrap, else Landlock, else hardened pods, never with weaker isolation than asked.
- **Server and tools.** A single `evalsid` binary (Connect, gRPC and REST), a web UI, guardrails, annotation queues, webhooks, MCP tools, authentication and per-project credentials, and the `evalsi` CLI and Python SDK.
- **Kubernetes.** Helm charts (`evalsi`, `evalsi-crds`, `evalsi-sandboxd`), an operator with `EvalRun`, `OnlineEvalPolicy`, `Evaluator` and `SandboxClass` CRDs, and an air-gapped install bundle.
- **Release engineering.** Linux amd64 and arm64 archives, Python distributions, multi-architecture images and OCI charts, signed keylessly with Sigstore, with `scripts/verify-release.sh`.

### Security

- The API bounds every RPC message at 64 MiB, and reads at most 64 KiB of a request whose credential was rejected. Connect reads a unary request whole before authentication runs, so a caller without a valid credential could otherwise make the server buffer a body of any size.
- The operator lets a resource name a project other than its namespace (`evals.si/project`) only from the release's namespace or namespaces mapped with `operator.projectNamespaces`, since it acts through the API as an owner.
- The chart's bundled NATS requires a token, and a NetworkPolicy limits its client port to the release's namespace.
- Trace sources refuse shared address space (100.64.0.0/10, where some clouds serve instance metadata), 0.0.0.0/8 and NAT64 addresses of internal hosts unless listed in `sources.allow_hosts`.

### Known limits

See [docs/LEFTOVERS.md](docs/LEFTOVERS.md) for the full list and [SUPPORT.md](SUPPORT.md) for what has been verified. In particular, EKS and GKE have not been run, and the per-release sandbox-pool NetworkPolicy has not been exercised on a cluster that enforces NetworkPolicy.
