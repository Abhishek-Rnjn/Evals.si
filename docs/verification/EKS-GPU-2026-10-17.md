## OpenRLHF: current-stack limitation and faster control

The current OpenRLHF 0.11.2 vLLM extra pins vLLM 0.29.0. Its NVIDIA CUTLASS
4.6.2 dependency requires protobuf `>=6.30.2,<7`; the current SDK declares
protobuf `>=7.35`. Pip reproduced `ResolutionImpossible` for a combined
environment. This is a **same-environment integration/packaging limitation**,
not an EKS/GPU or reward-calculation failure.

HTTP rewards allow separate, dependency-consistent environments. However,
the current native stack also pins FlashAttention 2.8.3. Its official release
has no prebuilt Torch 2.13 wheel. The source build was still compiling after
approximately 50 minutes, with about 21 of 72 CUDA units completed and the
GPU idle. **The user requested cancellation.** Only that verified build
process tree was stopped; no dependency checks were disabled.

The faster control instead used the cached `vllm/vllm-openai:v0.11.0`
image and OpenRLHF 0.9.0's official vLLM pin. The matching official
FlashAttention wheel is checksum-pinned in
`tests/rlframeworks/requirements-gpu-openrlhf-prebuilt.txt`.
Installation and `pip check` passed without a CUDA source build.
`requirements-gpu-openrlhf.txt` records the attempted **current** stack
and the separate-process requirement; it is not a successful certification.

The SDK reward server ran in the existing clean SDK environment on loopback.
An audit wrapper delegated scoring unchanged and recorded only completion
lengths, labels and totals. Its HTTP negative/positive control returned
`[0, 1]`; four subsequent real trainer requests returned 1.

The native `openrlhf.cli.train_ppo_ray` invocation used:

```sh
--actor_num_nodes 1 --actor_num_gpus_per_node 1 \
--vllm_num_engines 1 --vllm_tensor_parallel_size 1 \
--colocate_all_models --enforce_eager --vllm_gpu_memory_utilization 0.25 \
--pretrain /work/models/qwen05 --remote_rm_url http://127.0.0.1:PORT/score \
--prompt_data /work/openrlhf-prebuilt-run/prompts.jsonl \
--input_key input --label_key label --apply_chat_template \
--micro_train_batch_size 1 --train_batch_size 4 \
--rollout_batch_size 4 --micro_rollout_batch_size 1 \
--n_samples_per_prompt 1 --max_samples 4 --max_epochs 1 --num_episodes 1 \
--advantage_estimator reinforce --gamma 0.99 --init_kl_coef 0 \
--zero_stage 2 --bf16 --attn_implementation sdpa \
--actor_learning_rate 0.0001 --lr_warmup_ratio 0 --l2 0 \
--prompt_max_len 96 --generate_max_len 16 \
--save_path /work/openrlhf-prebuilt-run/final \
--ckpt_path /work/openrlhf-prebuilt-run/checkpoints \
--save_steps 1 --save_hf_ckpt \
--use_tensorboard /work/openrlhf-prebuilt-run/tensorboard
```

The four JSONL input records requested two friendly sentences about gardens,
music, walking and reading, with `label: ""`. The SDK served
`tests/rlframeworks/reward-gpu-nonempty.yaml`. The controller initialized
Ray with eight logical CPUs, one GPU, a 512-MiB object store and dashboard
disabled, then ran the unmodified native CLI.

An initial control with default LR warmup exited 0 and saved a checkpoint
but did **not** change the inspected parameter. It was not counted as a
pass. Disabling warmup for this one-step probe produced the verified update
above. The native trainer exited 0. A subsequent Ray worker SIGTERM
diagnostic was retained in the evidence; no clean-shutdown/HA claim follows
from this single-step check. GPU memory returned to zero afterward.
