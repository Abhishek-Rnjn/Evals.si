## Product Findings

**EKS-F1. Rolling upgrade is not zero downtime.** A TLS-verified in-cluster
client made authenticated Evaluate calls against the Service, with no retries.
During v0.1.0 to `fcfd1aa`, 1,779 calls succeeded and two raised `URLError`.
The longest interval between successful responses was 1.120716 seconds, not a
precisely measured continuous outage. Errors were not masked or treated as zeros.
The API closes its listener on shutdown before endpoint removal has necessarily
propagated. A failing-before-fix Helm regression now requires a ten-second native
preStop sleep and a thirty-second termination grace. The fix and regression are
in the consolidated [PR #51](https://github.com/Abhishek-Rnjn/Evals.si/pull/51).

```text

Evaluate p50=9.480780ms p95=10.558821ms p99=12.045209ms
traffic Job: Failed, BackoffLimitExceeded (backoffLimit=0)
```

After the fixed hook was already present, a controlled API-only rollout passed:

```text
attempts=1799 successes=1799 errors={}
elapsed_seconds=180.038790 max_success_gap_seconds=0.108865383
Evaluate p50=9.477011ms p95=10.226013ms p99=11.342411ms
```

Old v0.1.0 pods do not acquire a preStop hook retroactively. This follow-up does
not reverse the original failure or certify a published N-1 pair or worker
compatibility.

**EKS-F2. KEDA uses a nonexistent bundled monitor with external NATS.** The
chart rendered every pool's ScaledObject against the bundled Service even when

`keda.natsServerMonitoringEndpoint` setting are included in PR #51; rendering
external NATS with KEDA now requires an explicit monitor. Focused Helm
regressions for EKS-F1 and EKS-F2 passed together on the consolidated branch.
Original separate proposals #49 and #50 were closed as superseded, not merged.

This probe is upgrade evidence only, not M4 throughput certification. All main
application pods subsequently became Ready without restarts. The main image was

no shared networking was changed, and no CRD parity pass was claimed for the
initial stock profile. API parity was tested separately. The later isolated
trusted-network workaround passed CRD parity, as recorded below, without
certifying the stock restricted profile.

- The requested repository load command starts its own server in `TestLoad`;
  running it on the laptop would not certify the deployed EKS service. No such
  stand-in result is claimed as cluster load evidence.

  amd64 node found no `/dev/kvm` and no virtualization CPU flag. Other nodes were
  not probed; no metal provisioning was authorized. No real SWE-bench task ran.
- RDS Multi-AZ failover: no isolated RDS instance supplied or created.
- OIDC-provider UI login, SageMaker, Databricks and a real model/judge: access
  references were not supplied; permission to install software is not credentials.
- Further load/scaling was explicitly deferred by the operator. M4 throughput,
