## Product Findings

**EKS-F1. Rolling upgrade is not zero downtime.** A TLS-verified in-cluster
client made authenticated Evaluate calls against the Service, with no retries.
During v0.1.0 to `fcfd1aa`, 1,779 calls succeeded and two raised `URLError`.
The longest interval between successful responses was 1.120716 seconds, not a
precisely measured continuous outage. Errors were not masked or treated as zeros.
Root cause and a regression test are under investigation; no fix is claimed.

```text

upgrade_end=2026-10-12T13:18:03Z
```

This probe is upgrade evidence only, not M4 throughput certification. All main
application pods subsequently became Ready without restarts. The main image was
built from the pinned checkout using the stock Dockerfile, version
`0.1.0.post20261012`, and pushed to a tagged disposable ECR repository after GHCR
anonymous push was denied. Observed main digest:
`sha256:a339258b1f661693e2ab339151ffe73bf29b5239ec136a3b2e7dc72fb31022a9`.
The released sandboxd chart digest was
`sha256:3eb04d52983a13c9a0ab6b248dd30c23400ba6a2736e2e249ccfddee48432572`.

Startup errors were connection refusals while bundled ClickHouse/NATS started.
They stopped after dependencies became Ready; no independent product finding
has been established for those initial restarts.

## Environment Problems And Not Run

**EKS-R1. Control plane cannot dial Calico overlay webhook pods.** Reproduced
with the parity EvalRun while the operator was Ready and the EndpointSlice
reported a Ready pod on port 9443. Calico uses IP-in-IP `Always`, VXLAN `Never`.
[Tigera's EKS documentation](https://docs.tigera.io/calico/latest/getting-started/kubernetes/managed-public-cloud/eks)
states that EKS control-plane nodes cannot initiate connections to Calico
networking pods, and suggests `hostNetwork: true` for trusted webhooks. Host
networking conflicts with PSA restricted. No webhook or PSA control was disabled,
no shared networking was changed, and no CRD parity pass is claimed. API parity
was tested separately, not as a replacement for the failed admission check.

- The requested repository load command starts its own server in `TestLoad`;
  running it on the laptop would not certify the deployed EKS service. No such
  stand-in result is claimed as cluster load evidence.
- Stock Firecracker and VM SWE-bench: existing nodes are regular EC2, not metal;
  KVM has not been probed. Metal provisioning is not authorized within the cap.
- RDS Multi-AZ failover: no isolated RDS instance supplied or created.
- OIDC UI login over HTTPS, SageMaker, Databricks and a real model/judge: access
  references were not supplied; permission to install software is not credentials.
- KEDA, three-node NATS and alert firing: not yet run.
- Load, concurrent agent trials, reward scale, retention/quota/redaction and
  source checks: not yet run.
- D10 full identity/run recovery: not yet run.
