# EKS leftovers verification, 2026-10-17

Bounded checks of `main@9718395` and the checkpoint fix on
`verify/eks-leftovers`. PR #85's multi-service environment work was excluded.
This is not M4, training, mesh compatibility or production-scale certification.
Account IDs, cluster endpoints and credentials are omitted.

## Setup

- Kubernetes `v1.36.4-eks-b9510e3`, Amazon Linux 2023, containerd 2.3.5.
- Calico 3.32.1 and Istio ambient 1.30.4; no namespace-wide STRICT policy
  was added. Existing policies and workloads were not modified.
- One available `g6e.xlarge`: NVIDIA L40S, 46,068 MiB, driver 580.178.04.
  GPU allocation required the `nvidia.com/gpu=true:NoSchedule` toleration.
- Native macOS kubectl 1.36.0, Helm 4.2.4 and Go 1.26.9. The earlier
  `/usr/local/bin/kubectl` was a Linux binary; Homebrew's binary was used.
- The supplied kubeconfig's exec environment used the supplied AWS profile.
  AWS credentials and token generation worked before Kubernetes access did;
  discovery succeeded after the owner restored access.
- Owned namespaces: `evalsi-verify-20261017` (baseline, checkpoint tests) and
  `evalsi-chart-20261017` (privileged, trusted host-network operator).
- The application used the source charts and released `evalsi:0.2.0` image,
  one CPU worker initially, TLS, authenticated NATS and one 1-GiB gp3 volume.
  Judge/harness workers were disabled. API SQLite storage was ephemeral:
  this fixture cannot establish run durability across replacement.
- The checkpoint controller was the locally built current Go operator,
  watching only the checkpoint namespace, with other controllers, webhooks
  and leader election disabled. This verifies real API reconciliation and
  GPU serving, not a newly published operator image.

## Checkpoint bug and replay

The stock image is
`vllm/vllm-openai:v0.11.0`, observed digest
`sha256:014a95f21c9edf6abe0aea6b07353f96baa4ec291c427bb1176dc7c93a85845c`.
Its entrypoint is `python3 -m vllm.entrypoints.openai.api_server`.
The operator supplied positional `vllm serve` arguments but did not run that
CLI, so the positional name was not promoted to the API server's `model`.
The fix explicitly defaults the command to `["vllm", "serve"]`; an explicit
`spec.command` remains unchanged.

Build the current operator with `go build -o /tmp/evalsi-operator
./cmd/evalsi-operator`, install the checkpoint CRD, create a dedicated
baseline namespace, and run:

```sh
/tmp/evalsi-operator --controllers=checkpointserver \
  --watch-namespace="$NS" --namespace="$NS" --webhooks=false \
  --leader-elect=false --metrics-bind-address=0 \
  --health-probe-bind-address=127.0.0.1:18091
```

The exercised resource spec was:

```yaml
apiVersion: evals.si/v1alpha1
kind: CheckpointServer
metadata:
  name: opt-smoke
spec:
  image: vllm/vllm-openai:v0.11.0
  model: facebook/opt-125m
  servedModelName: checkpoint-smoke
  resources:
    requests: {cpu: "1", memory: 4Gi}
    limits: {cpu: "2", memory: 12Gi, nvidia.com/gpu: "1"}
  nodeSelector:
    node.kubernetes.io/instance-type: g6e.xlarge
  tolerations:
    - {key: nvidia.com/gpu, operator: Equal, value: "true", effect: NoSchedule}
  args: [--enforce-eager, --max-model-len, "128", --max-num-seqs, "2",
         --gpu-memory-utilization, "0.2", --dtype, half]
```

Apply in `$NS`, wait for Ready, and forward its Service's port 8000.
Assert both `/v1/models`'s root and a successful completion. Then create a
random `api-key` Secret and set `spec.apiKeySecret` to exercise the keyed
rollout. Delete the resource and wait for its children to disappear.
The image pull took about 4m35s; cached model startup was much shorter.
