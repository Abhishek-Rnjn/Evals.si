# Harness² verification: upstream workflow and real OpenCode

Date: 25 October 2026. This is a bounded integration study, not a benchmark,
security certification, or evidence that recursive harness optimization improves
a real application.

## Decision

**Partially verified.** Evals.si can read the pinned upstream deterministic
workflow's actual files, preserve missing/error grades, compare its results,
and attribute a physically executed script ablation. Real OpenCode 1.19.3 with
Sonnet also completed a synthetic tool/file task through Evals.si's bwrap
sandbox, model-host allowlist and hidden checker.

Do not mark the complete Harness² guide or its WorkBuddy/Codex examples verified.
The real-model executor smoke and deterministic upstream refinement are
**separate experiments**. No paid model ran the upstream refinement loop, no
real benchmark was downloaded, and no benchmark judge or human calibration ran.

The sandbox reports `driver: bwrap`, `level: namespaced`, network allowlist
through its logging proxy, and a read-only system root. It explicitly reports

that is not a production deployment recommendation or a claim that a normal
container has the needed namespace privileges.

The synthetic task gate was only `task-success >= 1`. A successful task with
an egress denial must not be described as a clean policy pass. Production specs
that require both must also gate `policy-violations.policy-clean`.

## Actual startup failure and correction

The original OpenCode example declared `memory_mb: 4096`. Measured independently
of Evals.si inside the same Linux image:

```bash
prlimit --as=2147483648 -- opencode --version
# exit 133, Trace/breakpoint trap
prlimit --as=4294967296 -- opencode --version
# exit 134, JavaScriptCore MemoryExhaustion assertion
prlimit --as=8589934592 -- opencode --version
# exit 0, 1.19.3
```

The actual Evals.si OpenCode task also exited 133 at 2 GiB, before any usable
agent trajectory. Raising the sandbox allowance to 8192 MiB allowed the scripted
and real Sonnet tasks to finish. The example is corrected and a regression test
first failed against its original 4096-MiB value, then passed after the fix.

On this bwrap fallback the memory limit is **virtual address space
(`RLIMIT_AS`)**, not an RSS promise. Bun's reservations are not the same as
resident consumption. This study kept a separate outer 4-GiB RAM cap; it does
not weaken sandbox limits, remove the namespaced floor or change Go's resource
enforcement. Different runtime versions/architectures can require different
measurements, and the template is not a universal sizing recommendation.

The runtime still attempted a denied npm registry request despite disabling
model fetching/default plugins and supplying explicit model configuration.
Do not silently broaden the runtime allowlist to make policy checks green.
Pre-seed required artifacts or explicitly review the additional host access.

## Reproduce the no-cost upstream acceptance

Use a separate upstream checkout, not a guessed hand-written namespace:

```bash
git clone https://github.com/google-research/harness2.git /tmp/harness2-upstream
git -C /tmp/harness2-upstream checkout 1cfe254e8d25b15f37048c3730134686abe60335

# From this repository, with Python 3.12 and uv:
cd python
uv sync --locked --all-packages --python 3.12
cd ..
python/.venv/bin/python scripts/check-harness2-upstream.py \
  --upstream /tmp/harness2-upstream \
  --output /tmp/harness2-verification-new
```

The output must not exist. The script verifies the exact upstream revision,
executes its deterministic workflow and independent checker, checks resume,
missing/error grades, physically executes both revert variants, and invokes
the actual matrix/calibration CLI. It writes local evidence and makes **zero
provider calls**. It executes code from the supplied checkout; review/trust
that pinned upstream revision before running it.

CI runs the same command using a separately checked-out pinned upstream tree.
That automated job does not install OpenCode, use paid credentials or claim a
live-model pass.

## Validation commands

Commands were run from the verification worktree with its SDK and harness source
on `PYTHONPATH`, using the application-first worktree's locked Python environment.

- `python -m unittest discover -s tests -q` in the pinned upstream checkout:
  **5 passed**.
- Focused importer/CLI/calibration tests: **32 passed**.
- Related matrix/ablation/readers/benchmark/follower tests: **91 passed** before
  adding the memory regression.
- Combined focused suite after the example correction: **124 passed**.
- `scripts/check-harness2-upstream.py --upstream ... --output ...`:
  real workflow, judge files, grade fault controls and executed ablations passed.
- Actual `evalsi matrix ... --gate --format json`: positive **exit 0**,
  reversed negative **exit 1**.
- Actual `evalsi run -f run.json --output results.json` inside the owned
  privileged development container: scripted/real Sonnet **exit 0**; deliberately
  wrong file **exit 3**. No fabricated success fallback was used for failures.
- Real `Follower.flush()` against current-source `evalsid`, then
  `evalsi policy stats harness2-follow-latency --server ...`: persisted trace and
  **one evaluated trace** verified after ingest grace. An immediate trace fetch
  initially returned 404 before grace elapsed, then returned 200.
